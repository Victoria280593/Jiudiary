# Мастер-промпт для работы с бэком JiuDiary

Ты работаешь с бэкендом JiuDiary. Всегда сохраняй существующую архитектуру, стиль кода и договорённости проекта. Если в бэке не хватает информации для корректного решения или есть несколько архитектурно разных вариантов — сначала спроси у владельца проекта. Не додумывай доменную логику молча.

## Архитектура

- Бэкенд разделён на API и библиотеки.
- API находится в отдельной папке `back/api`.
- Библиотеки находятся в `back/libs`.
- Библиотека базы данных находится в `back/libs/database`.
- DTO/input/output модели находятся в `back/libs/models`.
- Контроллеры должны быть тонкими: принять input model, получить текущего пользователя из base controller/auth context, вызвать сервис, вернуть output model.
- Основная бизнес-логика должна находиться в сервисах.
- Работа с EF Core и запросами к базе должна находиться в сервисах, не в контроллерах.
- DI-регистрация сервисов должна быть вынесена в extension-методы, например `ServiceCollectionExtensions.AddServices`.
- Новые сущности базы добавляются в `database`-библиотеку и регистрируются через `DbSet` в `DbContext`.
- Ограничения моделей базы по возможности описываются атрибутами в entity-классах: `Key`, `ForeignKey`, `DatabaseGenerated`, `Required`, `MaxLength`, `Table` и т.д.
- `OnModelCreating` использовать только там, где атрибутов недостаточно.

## Стиль кода

- Сигнатуры методов писать в одну строку.
- Не использовать record для DTO. DTO должны быть полноценными классами.
- Для каждого публичного API-метода создавать отдельные модели:
  - `...InputModel` для входных данных;
  - `...OutputModel` для результата.
- Названия моделей должны явно показывать назначение метода.
- Не возвращать EF entity наружу, если метод является новым или можно безопасно использовать DTO.
- Ошибки и сообщения пользователю писать на русском языке.
- Логи писать через `ILogger<T>`; параметры в сообщениях разделять `|`.
- Комментарии XML обязательны для публичных классов, публичных методов и публичных свойств моделей.
- Не писать лишнюю бизнес-логику в контроллерах.
- Не смешивать несколько body в одном HTTP-методе. Если нужен файл и данные — использовать `multipart/form-data`; если нужен JSON — один `InputModel` через `[FromBody]`.

## EF Core и база данных

- Для выборок использовать `AsNoTracking`, если данные не изменяются.
- Проекции делать через `Select` в output model и завершать `ToListAsync`, `FirstOrDefaultAsync` и т.п.
- Не тащить лишние данные через `Include`, если можно спроецировать нужные поля.
- Для вложенных коллекций, сложных `Distinct`, `GroupBy` и проблемных projection лучше разделять запросы на несколько понятных запросов, чем заставлять EF переводить сложную конструкцию.
- Nullable-поля в базе должны быть nullable и в C# модели. Не ставить `[Required]` на nullable-свойства.
- SQL-скрипты для изменения базы класть в `back/scripts` и делать безопасными для повторного запуска, если это возможно.
- Не дропать таблицы или данные без явного разрешения владельца проекта.

## Авторизация и пользователь

- Пользователь должен браться из JWT/base controller/auth middleware, а не передаваться строками, если это код внутри JiuDiary.
- Роли проверять явно в сервисе, если метод доступен только определённой роли.
- Для разных причин отказа писать разные ошибки на русском языке.

## Git и деплой

- Если создаёшь ветку для бэка, в названии должна быть область `back`, например `codex/back-kratkoe-opisanie`.
- Коммиты писать на русском языке.
- В коммите явно отражать область изменения, например: `Бэк: добавить создание группы`.
- Не пушить без просьбы пользователя.
- Перед коммитом по возможности запускать `dotnet build`.

## Поведение помощника

- Если задача касается бэка и есть неоднозначность в доменной логике, схеме базы, ролях, миграциях или формате API — спроси у владельца проекта.
- Если вопрос касается только технической реализации в рамках уже принятого стиля — действуй сам.
- Не переписывай существующую архитектуру без явной команды.
- Не вноси масштабные рефакторинги вместе с маленькими фичами.
