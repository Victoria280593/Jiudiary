# Мастер-промпт для работы с фронтом JiuDiary

Ты работаешь с фронтендом JiuDiary. Всегда сохраняй текущий стиль интерфейса, структуру компонентов и уже реализованную логику. Фронтовые решения принимай самостоятельно, если задача понятна и не требует изменения доменной логики бэка.

## Общий стиль приложения

- Светлая тема.
- Тёплые пастельные оттенки.
- Большие радиусы скругления.
- Мягкие тени.
- Много воздуха.
- Никаких тяжёлых границ и визуального шума.
- Интерфейс должен быть спокойным, минималистичным и аккуратным.

## Архитектура фронта

- Не переписывать существующую логику без необходимости.
- Компоненты держать небольшими и понятными.
- Общие client-side состояния выносить в provider/client helpers, если данные нужны нескольким компонентам.
- Данные, которые уже загружены и должны жить на клиенте, хранить в состоянии и обновлять точечно после create/update/delete, а не перезапрашивать без причины.
- API route handlers использовать как BFF-слой между фронтом и бэком.
- Перед изменением Next.js-кода учитывать локальные правила проекта и документацию текущей версии Next.js из `node_modules/next/dist/docs`.

## UI и адаптивность

- Desktop-версию не ломать при изменениях мобильной версии.
- Для мобильной версии использовать отдельные responsive-классы, не меняя поведение больших экранов.
- Избегать горизонтального скролла страницы на телефонах.
- Использовать `flex`, `grid`, `gap`, `flex-wrap`, адаптивные классы и относительные размеры.
- Если ширины не хватает, элементы должны переноситься, а не превращаться в горизонтальную прокрутку, если пользователь явно не просил scroll.
- При изменении календаря сохранять текущую бизнес-логику и менять только расположение/визуал, если задача не требует большего.
- При кликах, сохранениях и удалениях состояние UI должно обновляться сразу и корректно.
- Не добавлять лишние надписи о загрузке/обновлении, если пользователь просил этого не делать.

## Формы и данные

- Для форм использовать понятные русские подписи.
- Не писать слово `стандартное`, если пользователь просил нейтральные подписи вроде `Время начала` и `Время окончания`.
- Если данные очевидны из контекста UI, не заставлять пользователя вводить их повторно. Например, дата тренировки берётся из выбранного дня календаря.
- После create/update/delete обновлять локальное состояние так, чтобы UI не показывал устаревшие данные.
- Ошибки пользователю писать на русском языке.

## Работа с бэком

- Для новых API-вызовов использовать существующие helpers в `src/lib` и route handlers в `src/app/api`.
- Не менять контракт бэка без необходимости.
- Если контракт бэка непонятен или требует доменного решения — уточнить у владельца проекта.
- Если можно решить фронтовую задачу без изменения бэка — решать на фронте самостоятельно.

## Git и деплой

- Если создаёшь ветку для фронта, в названии должна быть область `front`, например `codex/front-kratkoe-opisanie`.
- Коммиты писать на русском языке.
- В коммите явно отражать область изменения, например: `Фронт: улучшить мобильный календарь`.
- Не пушить без просьбы пользователя.
- Перед коммитом запускать production build фронта.

## Поведение помощника

- Фронтовые визуальные решения можно принимать самостоятельно и показывать результат пользователю.
- Если пользователь говорит `попробуем`, не пушить без отдельной просьбы.
- Если пользователь просит `сразу запуш`, после успешной сборки сделать коммит и push.
- Не смешивать несвязанные изменения в один коммит.
